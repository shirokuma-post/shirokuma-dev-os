# 手元の API を通して確かめる

DB の役を切り替えるだけでは、公開されるスキーマ・トークンの検証・HTTP の返り方・関数の公開・ファイルの取得経路までは見えない。`supabase start` が立てた手元の PostgREST を通し、[pgtap.md](pgtap.md) の試験とは別に確かめる。Storage は PostgREST とは別の API なので、DB の試験だけで代わりにしない。

## 使い捨ての環境と関門（2 段）

専用の作業場所で空の環境を立て、本番と同じスキーマ・公開設定・権限を流す。本物のデータや鍵は持ち込まない。自動の seed は止める。**ログイン・利用者作成・データ作成の前**に、次を両方通す。

1. **URL が localhost か**。今回の `supabase start` の出力から API と DB の URL を読み、URL として解析する。ホストは `localhost` / `127.0.0.1` / `::1` だけ、ポートは今回起動した値だけを許す。文字列の前方一致・部分一致で判定しない。利用者情報付きの URL・別ホスト・未定義の URL・想定外の方式は、接続前に失敗させる。`localhost` の解決先もループバックだけであることを確かめる。
2. **データが空か**。同じ環境の DB に管理側で直接接続し、本番で必ず 1 件以上ある表が 0 件であることを確かめる。API の一覧が 0 件でも、RLS が隠しているだけかもしれない。表が無い・数えられない時は止める。

API と DB が同じ起動環境の物であることを、起動情報と照合する。両方が手元でも別の環境なら止める。DB の関門の注意点は [postgres.md](postgres.md) と [pgtap.md](pgtap.md) を参照。

すべての HTTP 呼び出しを同じ入口に集め、毎回完成した URL を検査する。認証・関数・Storage・取得用 URL も対象。相対パスは検査済みの起点から組み立て、途中で別の起点に置き換えられないようにする。自動リダイレクトと外向きのプロキシを使わず、接続がループバックに閉じることを確かめる。返された取得用 URL も、そのまま追わない。

外の URL は通信前に止まること、データが 1 件ある使い捨て環境では認証や seed より前に止まること、止まった後に変更が無いことを先に確かめる。手元から外部へ中継するトンネルは使わない。

## 身元を分ける

- 公開の鍵だけを持つ未ログインの呼び出しと、同じ公開の鍵に利用者のアクセストークンを加えた呼び出しを分ける。公開の鍵は利用者の身元ではない（[鍵の役割](https://supabase.com/docs/guides/getting-started/api-keys)）。
- 合成の利用者を 2 人作り、手元の認証 API でそれぞれログインする。DB の補助関数で作った身元やクレームを、そのまま API の認証を通した証拠にしない。
- 1 人目を持ち主、2 人目を別の利用者とする。同じテナントと別テナントの条件は別々に作る。必要なら下位の所属や役も変える。
- 利用者ごとにクライアントとセッションを分ける。直前のログイン情報が残っていないか、呼び出し前に確かめる。トークンや応答の中身は記録に残さない。
- 管理用の鍵は合成データの準備と結果の読み取りだけに分離する。RLS の判定には渡さない。管理側による成功を、利用者の陽性対照にしない。

## 経路と約束の一覧の対応

[約束の一覧](promises.md)から、対象に当てはまる番号を `P<n> [A1,C1]` の形で付ける。下表は確認する観点であって、具体的な攻めのリクエストではない。

| 通す経路 | 一覧の番号 | DB 側の試験に加えて見る所 |
|---|---|---|
| 公開の鍵だけ・利用者トークン付き | C1,C2,C3 | 未ログインとログイン済みの扱い、実際のトークン検証、身元と役の対応。HTTP の方式ごとの挙動も見る |
| 2 人目からの取得・一覧・検索 | A1,A2,A3,A4 | 同じ公開設定を通した時の見える行・件数・存在の返り方。空の応答と、経路が存在しない失敗を分ける |
| 2 人目からの作成・更新・削除 | B1,B2,B3,B4 | 身元と所有者の対応、変更できる項目、実際に変わった行。応答の成功だけで判断しない |
| 公開された関数の呼び出し（RPC） | A1,A2,B1,B2,C4,E4 | 関数が公開される範囲、呼べる役、引数と身元の扱い、関数内の RLS・権限、応答の情報。表の API と同じ守りとは限らない |
| 一覧・集計・関数での取得量 | A3,D1,D2,D3 | 件数や範囲の指定を API がどう解釈するか、経路・身元をまたぐ上限。単発の DB 試験で時間当たりの制限まで確認済みにしない |
| Storage の一覧・取得 | A1,A2,A3,A4,C1 | 非公開の物が別の利用者に見えないこと。公開設定と取得用 URL の経路も分ける |
| Storage の作成・更新・削除 | B1,B2,B3,B4,C4 | 実際のファイル操作に対する所有者と役の制限。DB のメタデータだけの成功・拒否で判断しない |
| 失敗応答・記録 | E1,E2,E3,E4 | HTTP のエラー内容、失敗時の記録と本来の処理。記録の有無に応じて約束を選ぶ |
| 手元の待ち受け | F1 | API と関連サービスが IPv4 / IPv6 とも手元に閉じること。URL の検査だけで待ち受けの範囲まで確認済みにしない |

Storage の[権限の仕組み](https://supabase.com/docs/guides/storage/security/access-control)も確認する。公開のファイルと非公開のファイル、期限付きの取得 URL は期待する公開範囲を先に約束にする。公開を許した物の取得成功を BROKEN にせず、非公開の拒否で公開の経路まで検証済みにもしない。

B5 の並行実行や F2,F3 の外部との境界は、上の基本経路だけでは確認できない。当てはまるなら別の決定論的な試験を足し、対象が無ければ理由を残す。対応番号が付いていても、その項目全体を網羅したという意味にはしない。

## 審判と固定

1. 各経路で、正しい利用者による同じ操作と期待する結果を先に確認し、通った時だけ `CONTROL P<n>: OK` を出す。2 人目自身のデータも正常に扱えることを確認する。
2. 約束に沿って HTTP の状態・結果件数・操作後の状態を比較する。書き込みの拒否は、対象が変わっていない所まで管理側で読み取る。通信失敗・未公開の経路・想定外の入力エラーを、RLS が守った証拠にしない。
3. 判定は既存の `HELD` / `BROKEN` / `INCONCLUSIVE` / `ERROR` を使う。約束ごと・経路ごとに集約し、1 件でも破れれば BROKEN。陽性対照の無い HELD は確定しない。
4. 決定論的な試験を [ci.md](ci.md) の流れに固定し、失敗は非 0 にする。判定不能も固定試験では緑にしない。`coverage.mjs` には既存の形式のログを渡し、試した経路と未検証の条件を報告する。
5. 守りがある版で緑、対応する守りを外した版で赤になることを、API を通して再確認する。DB 側だけのミューテーションの結果で代用しない。

API の呼び出しは複数のトランザクションに分かれる。DB の `ROLLBACK` で認証やファイルまで戻せるとは考えず、終了時・失敗時とも専用の環境と保存領域を捨てる。残すのは約束番号・経路・結果・件数だけ。
