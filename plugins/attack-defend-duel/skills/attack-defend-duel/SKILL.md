# Attack-Defend Duel — 別の頭に攻めさせ、自分は審判をする

> 自分で書いた守りを自分で攻めると、同じ思い込みで同じ穴を見落とす。
> 攻め役を別の AI に任せ、守り役は「約束を書く・走らせる・壊して試験が効くか見る・直す・固定する」に専念する。

## なぜ役を分けるか

- **見落としの相関を切る**: 守りを書いた頭は、自分が想定した攻め方しか試さない。別の頭は別の手筋を持ってくる。
- **書き上がる物の向きが違う**: 同じ「破れるか」の確認でも、攻め役が書くのは「この順でこう引けば破れる」という手順、守り役が書くのは「この守りを外せば試験が赤になる」という確認。Claude は前者を書くと安全側の判定で止められることがある。攻め手は攻め役に書かせ、Claude は**読んで・走らせて・判定する**側に立つ。
- ★ Claude が止められた時は、言い換えて押し通さない。その部分を攻め役に回し、止められたことを人に報告する。

## 縛り（全部守る）

1. **走らせるのは使い捨ての環境だけ。隔離は環境の側で先に作る**。手元のコンテナ・エミュレータ・空の DB。本番・共有ステージング・他人と共用の DB では回さない。
   - 試験を回す場所に、本番の接続先・鍵を置かない（CI の secret にも、試験を回す script が読む env にも）
   - 接続は使い捨ての環境だけに届く形にする（unix socket だけ・手元のアドレスだけ・試験を回す script が自分で立てた環境だけを見る）
   - 下の関門は、この隔離をすり抜けた事故を止める**最後の止め**であって、安全の根拠ではない
2. **全ての試験に「本番に流れたら止まる関門」を 2 段で入れる**。試験の最初（データを作る前）で、両方を満たさなければ即座に失敗させる。関門の無い試験は走らせない。
   - **1 段目 = 環境の印**: 使い捨ての環境を立てる時にだけ付ける印があるか（Postgres の `cluster_name`・MySQL の `report_host`・Firebase の `demo-` プロジェクト・接続先が手元のアドレスか）。印は、試験の中から書き換えられない物を選ぶ（起動時にしか決められない設定）
   - **2 段目 = データ**: 本番で必ず 1 件以上ある表が 0 件か
   - 片方だけでは足りない。データだけだと「立ち上げたばかりで本番がまだ空」の時に素通りし、印だけだと印を付け忘れた共有環境を見分けられない
   - 形は環境ごとに `references/` を見る
3. **攻め役に渡すのは約束・スキーマ・守りのコードだけ**。本物のデータ・鍵・`.env`・接続文字列は渡さない。
4. **攻め役の書き込み先を 1 つのディレクトリに限る**（フルパスで指定する）。リポジトリ本体・デプロイ用の作業場には書かせない。相対パスや「〜のフォルダ」という言い方は、別の場所に書かれる原因になる。
5. **攻め役の出力は全部読んでから走らせる**。外部への接続・ファイルの読み書き・権限の変更・破壊的な DDL が無いかを見る。
6. **記録は結果だけ**。破れた/破れない・件数・どの約束か。取り出したデータの中身は残さない。
7. **攻めの手順を外向けの文書に写さない**。記事・講座・配布物に載せてよいのは段取りと結果だけ。

## 段取り

### 0. 準備

作業場所を 1 つ作り、`in/`（攻め役に渡す物）と `out/`（攻め役が書く場所）を分ける。

```bash
RUN="$HOME/duel/$(date +%Y%m%d_%H%M)_<対象>"
mkdir -p "$RUN/in" "$RUN/out"
```

使い捨ての環境を立て、本番と同じスキーマ（データは空）を流す。立て方は `references/` の該当ファイル。

### 1. 約束を書く（守り役）

約束は試験の範囲そのもの。**約束に書かなかった穴は探されない**。まず `references/promises.md` の一覧から当てはまる物を拾い、足りない物を足す。

`$RUN/in/promises.md` に、守っているはずの約束を **1 行 1 件・番号付き**で書く。「〜できない」「〜だけ」で終わる、試験で白黒が付く形にする。

- P1: 別のテナントの利用者は、一覧で 0 件
- P2: 未ログインの利用者は、記録の関数を呼べない
- P3: 利用者は自分の記録しか作れない・変えられない
- P4: 記録の失敗があっても、本来の応答は返り続ける

対象のスキーマ・権限の定義・守りのコード（関数・ミドルウェア・ルール）を `$RUN/in/` に写す。手本になる既存の試験が 1 本あれば一緒に渡す（データの作り方と役の切り替え方を真似させるため）。

### 2. 攻めさせる（攻め役）

依頼文は固定の雛形 `scripts/attack-prompt.txt` にある。**Claude は依頼文を書き起こさず、置き場所と関門の形だけを渡してスクリプトを走らせる**:

```bash
node <このスキル>/scripts/run-attacker.mjs "$RUN" "<関門の形>"            # Codex CLI で起動
node <このスキル>/scripts/run-attacker.mjs "$RUN" "<関門の形>" --print    # 依頼文を表示するだけ (他の AI に渡す時)
```

- 関門の形は `references/` の該当ファイルにある物を 1 文で書く (例: `cluster_name が rls-disposable でなければ例外で止め、本番に必ず 1 件以上ある表が 0 件でなければ止める`)。
- スクリプトは `$RUN/in/promises.md` と `$RUN/out/` が無ければ起動しない。標準入力は閉じて渡す (開いたままだと Codex が追加の入力を待って止まり続ける)。
- 終了コード 3 = 攻め役が `$RUN/out/` の外に file を足した・変えた (攻め役の側の hook 等。2026-10-20 実例: Codex の dev-os hook が `DECISIONS.md`)。名指しされた file は攻め役の出力として扱わず、走らせない。 起動の記録 (標準出力の書き出し先) は `$RUN/out/` の中か `$RUN` の外に置く (`$RUN` 直下に書くと、それ自体が名指しされる)。
- 雛形を直す時は `attack-prompt.txt` を直す。SKILL.md に依頼文を写さない (2 か所に置くとずれる)。
- ★ **ここで Claude が止められたら、言い換えて押し通さない。** 同じコマンドを人に打ってもらう (コマンドを 1 行で示す)。攻め役の出力が `$RUN/out/` に揃ったら、審判から再開する。

### 3. 審判（守り役）

1. `out/` の全ファイルを読む（縛り 5）。関門が無い file は走らせない。
2. 使い捨ての環境で 1 本ずつ流し、出力を `$RUN/out/judge.log` に集める。判定は人や AI の読みでなく、道具で決める:

   ```bash
   node <このスキル>/scripts/coverage.mjs "$RUN/in/promises.md" "$RUN/out/judge.log"
   ```

   - `HELD` は、同じ約束の `CONTROL P<n>: OK` が無ければ `INCONCLUSIVE` に落とす（陽性対照の無い HELD は「拒否された」以上のことを言えない）
   - `BROKEN` / `ERROR` が 1 つでもあれば非 0 で終わる
   - 終了コードも見る。`BROKEN` を出しても 0 で終わる試験は、CI に取り込む前に直す (2026-10-20 実例: Firestore の試験が BROKEN 7 件で exit 0)。
   - 関門は両向きで試す: 外の接続先・本番に見立てた状態 (データ 1 件) で止まり、その時に何も書き換えていないこと。
3. エラーは読み分ける: 試験の書き損じか、守りの穴か。権限で止まったのは HELD でよいが、どの権限で止まったかは確かめる。
4. 書き損じは**審判が直さず攻め役に戻す**。所見 (どの判定がなぜ試験の誤りか) を `$RUN/out/judge-notes.md` に書き、`node <このスキル>/scripts/run-attacker.mjs "$RUN" --retry` を走らせる。直しを頼む文も固定の雛形 (`scripts/attack-retry.txt`)。直った版をもう一度 1. から審判する。
   - 攻め役の環境は手元で待ち受け・接続できないことが多く (Codex の sandbox)、攻め役は自分の試験を流せない。書き損じは審判の最初の 1 回で出る前提で回す (2026-10-20 実例: 送り方の誤りで 5 本とも陽性対照が通らない / ヘッダ値の末尾の空白が通ると思い込んで誤った BROKEN)。陽性対照の ERROR は、守りでなく試験を疑う合図

### 4. 破れたら直す（守り役）

1. 守りを直す。直し方は「その攻め手を塞ぐ」でなく「約束が成り立つ構造にする」（例: 呼び出し側から渡された件数や持ち主を信用せず、守りの内側で数え直す）。
2. 環境を作り直して当て直し、同じ攻めの試験が `HELD` になるのを見る。
3. 直した物を、もう一度攻め役に攻めさせる（2. に戻る）。3 往復で収まらなければ人に上げる。

### 5. 試験が効くかを確かめる（守り役・ミューテーション）

`HELD` だけでは「試験が何も見ていない」可能性が残る。**守りを 1 か所ずつわざと外した版**を作り、試験が `BROKEN` を出すのを見る。

- 外し方の例: 権限を 1 つ開ける・行の絞り込み条件を消す・身元を引数から取るようにする・失敗の受け止めを消す・掃除の条件から持ち主を外す
- 外しても `BROKEN` が出ない時は、**試験が弱いのか、守りが二重なのか**を読み分ける:
  - 同じ絞り込みが後段でもう一度かかっている → 全か所外した版で確かめる
  - 上位の権限（スキーマや名前空間への入場）が先に止めている → 外した権限そのものは、権限を直接読む試験で見る
  - 失敗の受け止めが内側と外側の 2 段ある → 両方外した版で確かめる
- 二重の守りは悪いことではない。どの層が止めているかを結果に書く。

### 6. 固定する（守り役）

- 破れた約束だけでなく、**重要な境界（テナント・持ち主・役）の約束は、破れていなくても**試験を CI に取り込む（関門ごと）。直した守りが後の変更で戻った時に赤で気づくため。
- 取り込むのは決定論的な試験（同じ入力で同じ結果）だけ。攻め役に新しい手筋を考えさせる探索は、CI で毎回は回さない（守りを変えた時・定期の監査の時に回す）。
- 取り込みの雛形 = `references/ci.md`（使い捨ての環境を CI の中で立てる・印を付ける・終了コードで赤にする）。
- 関門は両向きで確かめる: 空の環境で通る・データを 1 件入れた環境で止まる・止まった後に何も変わっていない。
- 守りを直した変更と、それを固定する試験は、同じ変更として出す。

### 7. 片付けと報告

環境を止める。`$RUN/RESULT.md` に残す:

- `coverage.mjs` の表（約束ごとの判定と、約束の一覧のどの項目を確かめ・どれが未検証か）
- 破れた数と直したか / ミューテーションで赤を見た外し方（二重の守りはどの層か）

`notes.md` は次回の手筋の種になるので消さない。

## 確かめていない所を見せる

この段取りが保証するのは「書いた約束について、試した手筋では破れなかった」ことだけ。**攻め役が知らない攻め方を網羅できる保証はない**（攻め役のモデルを替えても、探索の独立性は上がるが、範囲の完全性は保証されない）。
だから結果は「何個破れたか」でなく、**どの守りの条件を確かめられていて、どれが未検証か**で報告する。

- 約束の一覧（`references/promises.md`）の各項目について、次のどれかを必ず付ける: 確かめた（`HELD` + 陽性対照）/ 破れた / 判定不能 / 試していない / 当てはまらない（理由）
- `coverage.mjs` が、`promises.md` の約束に付けた一覧の番号（`[A1,C2]` など）と判定の記録から、この表を機械で作る。一覧の項目で、どの約束にも付いていない物は「試していない」として表に出る
- 「試していない」が残ったまま「安全」と報告しない

## 環境ごとの差分

段取りは同じで、変わるのは「使い捨ての環境の立て方」「役（身元）の切り替え方」「関門の形」の 3 つだけ。

| 守りがある所 | 参照 |
|---|---|
| PostgreSQL の行単位セキュリティ（Supabase を含む） | `references/postgres.md` |
| pgTAP と補助関数で DB の試験を固定する（未実走） | `references/pgtap.md` |
| 手元の API を通して行単位の権限を確かめる（未実走） | `references/supabase-api.md` |
| MySQL / MariaDB の利用者ごとの権限・ビュー | `references/mysql.md` |
| Firebase のセキュリティルール（Firestore / Realtime Database / Storage） | `references/firebase.md` |
| アプリのコード（API のミドルウェア・ORM の絞り込み）。DB 側に守りが無い時 | `references/http-app.md` |
| （共通）約束の一覧 | `references/promises.md` |
| （共通）CI に固定する雛形 | `references/ci.md` |

4 枚とも 2026-10-20 に実地で 1 回ずつ回した（約束 4〜6・破れた 0・守りを 1 か所ずつ外したミューテーションで全件赤）。各ファイル冒頭に実測の内容を書いている。

**見つける力の実測（2026-10-20）**: 守りに目立たない穴を仕込んだ題材を 2 つ用意し、穴の中身を知らせずに攻め役（Codex）へ渡した。仕込んだ 4 個を 4 個とも見つけ、穴の無い約束を破れたと言う誤りは 0（アプリの API: 件数上限の抜け・OPTIONS の無認証 / Firestore: 一覧だけテナント条件なし・更新で持ち主を変えられる）。題材 2 つ・穴 4 個の小さな測定で、どんな穴でも見つかるという保証ではない。

**今のやり方との比較（同じ日・同じ題材）**: 同じ約束と同じ対象のコードを、コードを読むだけの監査（実行しない・別の AI）にも渡した → こちらも 4 個を 4 個とも見つけ、誤った指摘は 0。**小さな題材では、攻め守りの「見つける力」は読む監査を上回っていない**。
この段取りに残る違いは、見つけた後にある: 破れた所が**流せる試験**として残り CI で後戻りを止められること、守りを外して**試験が効くことを確かめられる**こと、判定を道具で決められること。読む監査は指摘の文章を残すだけ。
大きな題材（file をまたぐ守り・二重の守り・設定と実装のずれ）で差が出るかは、まだ測っていない。

守りが DB とアプリの両方にあるなら、両方で回す。DB 側が守れていてもアプリが管理者の鍵で DB を叩いていれば、守りの本体はアプリ側にある。

## やらないこと

- 本番・共有ステージングに攻めの試験を流す
- 攻め役の出力を読まずに走らせる
- 攻め役に本物のデータ・鍵を渡す
- 止められた内容を言い換えて書き直す
- 攻めの手順を外向けの文書・講座・配布物に写す
