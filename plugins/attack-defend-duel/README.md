# attack-defend-duel

守りの約束（行単位の権限・役ごとの権限・取得量の上限・記録の改ざん防止など）が本当に破れないかを確かめるスキル 1 本だけのプラグインです。フックは入りません。

- **攻め役**: 別の AI（Codex など）が、約束を破る試験を書く
- **審判役**: Claude が試験を全部読み、使い捨ての環境で流して判定する
- 破れたら守りを直し、守りを 1 か所ずつわざと外して試験が効くかを確かめ（ミューテーション）、CI に固定する

本番・共有のステージングには使いません。隔離は環境の側で先に作り（本番の接続先・鍵を試験の場所に置かない）、全ての試験に「本番に流れたら止まる関門」を最後の止めとして入れます。

結果は「何個破れたか」でなく、**どの守りの条件を確かめられて、どれが未検証か**で報告します。判定は 4 つ（破れた / 確かめた / 判定不能 / 試験が壊れた）で、正しい利用者なら通ることを確かめた陽性対照の無い「確かめた」は「判定不能」に落とします。この判定と表は `scripts/coverage.mjs` が機械で作ります。

## コードを読む監査との違い

見つける力で勝つ道具ではありません（下の実測では同じ題材で並びました）。違いは見つけた後に残る物です。

| | コードを読む監査 | この段取り |
|---|---|---|
| 残る物 | 指摘の一覧（読んだ人を信じるしかない） | もう一度流せる試験・CI の固定 |
| 試験が効く証拠 | 無い | 守りを外すと赤になることを確かめ済み |
| 判定 | 人や AI の読み | 道具が出す 4 つの判定と、確かめた所・未検証の所の表 |
| 直した後 | 読み直す | 同じ試験が緑に変わるのを見る・後戻りすれば赤 |

一度きりの点検なら読む監査で足ります。守りを変え続ける物で、後戻りを止めたい時にこちらを使います。

## 実測

- **見つける力**: 目立たない穴を仕込んだ題材 2 つ（アプリの API・Firestore のルール）を、穴の中身を知らせずに攻め役へ渡した → 仕込んだ 4 個を 4 個とも発見・誤った指摘 0。小さな測定なので、どんな穴でも見つかる保証ではありません
- **今のやり方との比較**: 同じ題材をコードを読むだけの監査にも渡すと、こちらも 4/4・誤り 0。小さな題材では見つける力に差は出ていません。この段取りの違いは見つけた後（流せる試験が残り CI で後戻りを止める・守りを外して試験が効くか確かめる・判定を道具で決める）にあります
- **試験が効くか**: 4 環境で、守りを 1 か所ずつ外した版を流し、全件で試験が赤になることを確認
- **関門**: 2 段（環境の印 + データ 0 件）。印は試験の中から書き換えられない設定を使う（PostgreSQL の `cluster_name`・MySQL の `report_host`）
- **発火**: `tests/run-trigger.mjs` で 10/10（守りを攻めて確かめる依頼 5 件で発火・無関係な依頼 5 件で発火しない）
- **判定の道具**: `tests/coverage.test.mjs` 38 本（判定の強さの順・陽性対照・一覧の項目の 5 つの状態・終了コード・書式の誤り）

## この段取りが保証しないこと

大きな題材（多数の file・守りが複数の層に分かれた物）で、読む監査より多く見つけるかは測っていません。見つける力の差は題材の作り方で大きく変わり、この段取りの価値の軸でもないため、測る予定もありません。

攻め役が知らない攻め方を網羅できる保証はありません。攻め役のモデルを替えても、探索の独立性は上がりますが、範囲の完全性は保証されません。だから「試していない」項目が残っている間は「安全」と報告しない決まりにしています。
