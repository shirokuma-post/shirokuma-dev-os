# アプリのコード（API が守っている時）

> 実地確認 2026-10-20（node:http の試験用アプリ・curl）: 攻め守り対戦 1 回。約束 5・破れた 0・守りを 1 か所ずつ外したミューテーション 5/5 で赤（テナントの絞り込み・持ち主を本文から取る・トークン無しを通す・件数上限・0.0.0.0 待ち受け）。関門は外の URL で止まった。

DB 側に行単位の守りが無く、アプリが 1 つの強い権限で DB を読んでいる時は、守りの本体は API のミドルウェア・認可の関数・ORM の絞り込み。攻める相手は DB でなく API。

## 使い捨ての環境

- アプリを手元で起動し、**空の DB**（コンテナ）に繋ぐ。本番・ステージングの DB の接続文字列を使わない。
- 外部サービス（決済・メール・AI など）は無効にするか、手元のモックに向ける。
- 試験用の利用者を 2 人以上（別テナント）作る手順を seed に入れる。

## 役（身元）の切り替え

試験用の利用者ごとにログインしてトークン（cookie）を得て、同じ API を役を変えて叩く。

- 件数上限の約束は、上限を越える件数を先に作ってから試す（seed が 3 件しかないと「50 件まで」は必ず守れて見える）。
- 待ち受けアドレスの約束は、curl だけでなく `lsof -nP -iTCP:<port> -sTCP:LISTEN` で実際の待ち受けを読む。IPv6 の `[::1]` も試す。

```bash
curl -s -H "Authorization: Bearer $TOKEN_A" http://127.0.0.1:3000/api/orders/<B の注文の id>   # 404/403 なら HELD
```

攻め役に試させる典型:

- 他人の id をパス・クエリ・本文に入れる（推測できる連番 id を特に）
- 本文に `tenant_id` / `owner_id` / `role` を混ぜる（サーバーがそれを信用して保存しないか）
- 一覧の件数上限・ページングの上限を越える値
- ログイン無し・期限切れ・別アプリのトークン
- 同じ操作の並行送信（1 回だけのはずの処理が 2 回通らないか）

## 関門

試験を回す script の最初で、接続先が手元であることと、DB が空から作られたことを確かめる。

```bash
case "$BASE_URL" in http://127.0.0.1:*|http://localhost:*) ;; *) echo 'not a disposable environment'; exit 1;; esac
```

アプリの DB にも同じく「必ず 1 行以上ある表が、seed 前に 0 行」を確かめる（`postgres.md` / `mysql.md` の関門）。

## 守りの層

- 認可のミドルウェア（全ての口にかかっているか・かかっていない口が無いか）
- データ取得の絞り込み（持ち主・テナントの条件を ORM の全クエリが付けているか）
- 本文からの値の受け取り方（持ち主・役をサーバー側で決めているか）
- 回数・件数の上限
