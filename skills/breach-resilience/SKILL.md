# Breach Resilience — 奪われた後の「届く範囲」と「止め方」

> 穴を探す監査は「入られないため」の点検。この skill は**入られた後**の点検。
> 鍵は漏れる・端末は失くす・token はログに残る。そのとき**どこまで届き、誰が気づき、誰が何を押せば何分で止まるか**を、
> 推測ではなく実測で表にし、足りない所を塞ぎ、止める手順を一度は実際に通しておく。

## 中核原則

1. **全部の鍵に同じ 4 列を埋める**: 届く範囲 / 気づき方 / 止め方（誰が・どの画面で・何を押す）/ 所要時間。1 列でも空なら、そこが今の弱点。
2. **届く範囲は実測で書く**: 「この鍵は読み取り専用のはず」は書かない。権限の一覧・ログ・実際に呼べた口で書く。言い伝えは監査の敵。
3. **AI は測る・人が押す**: ダッシュボードの操作、鍵の値の取り扱い、本番の鍵の無効化は人の手で行う。AI は前後の計測・手順書・見張りを受け持つ。鍵の値は画面にも file にも会話にも出さない（クリップボードから読み、読んだら消す script を使う）。
4. **漏れた時の被害を局所化する設計にする**: 1 本の鍵が全部に届く形（全テナントに届くアプリの合言葉・何でも読める管理鍵・本人と同じ OS user で動く CI）を、鍵を分ける・行の持ち主で縛る・返す列を絞る、で小さくする。
5. **「止めた」は記録で確かめる**: ボタンを押しただけでは止まっていない。無効化の前後でログを数え、旧い鍵の利用が 0・新しい鍵で正常、を 2 系統（別の担当・別の道具）で確かめてから完了にする。
6. **固定点検に落とす**: 一度の点検は風化する。token の一覧・メンバー・CI の secret 名・runner 名など「増えたら異常」の物は、毎週の固定点検で前回値と比べる。

## 進め方

1. **鍵と入口の棚卸し（読み取りだけ）**: 下の「対象の型」を自分のスタックに当て、実在する鍵・token・ログインの種類を名前と件数だけで一覧にする（値は見ない）。
2. **4 列を埋める**: 各行について、届く範囲を実測する（権限の付与・RLS・API の scope・その鍵で呼べる口の数）。気づき方が無い行、止め方が「分からない」行に印を付ける。
3. **高権限の口の台帳**: サーバーが強い権限（RLS を越える鍵など）で書く口を全部挙げ、各口に「認可の述語・行の持ち主の縛り・回数制限・監査の記録」があるかを表にする。台帳は「どこを突けば何ができるか」の地図なので、**repo に入れず**本人しか読めない場所に置き、repo には件数と項目だけを書く。
4. **塞ぐ順番**: ①合言葉なしで届くもの（ログインしただけ・公開の口）→ ②アプリ 1 本の鍵で他テナント・他アプリに届くもの → ③確認のすり抜け・記録漏れ。①の中では「外の人に届く」（メール・招待・送信の中継）を最優先にする。
5. **鍵の作り直し・型の移行**: 一度に切り替えない。段に分け、各段の前後で数える（→ `references/key-migration-stages.md`）。
6. **手順書を書き、1 本は実地で通す**: シナリオごとに 4 列 + 戻し方を `assets/runbook.template.md` の形で書く。少なくとも「利用者 1 人の全セッション失効」は試験用アカウントで実際に通し、所要時間を記録する。
7. **毎週の固定点検**: `assets/weekly-fixed-checks.template.md` を自分の環境に合わせ、週次の監査に組み込む。

## 対象の型（自分のスタックに当てて行を作る）

| 型 | 典型の届く範囲 | まず確かめること |
|---|---|---|
| 利用者のログイン（cookie / JWT） | その人が画面でできること | 利用者単位で全セッションを失効できるか（自前の token も含めて） |
| 運営者のログイン | 全テナント | 2 段階認証が DB の判定まで効いているか（画面だけでなく） |
| ソース管理の token | push・CI・runner 登録 | scope・本番へ出す経路の門・知らない版が本番に出たら気づくか |
| デプロイ基盤の token | 任意のコードを本番へ = 実行時の全 secret | token の一覧・期限・メンバー・知らない deployment の検知 |
| DB の管理鍵 | 全行の読み書き | その鍵だけを独立に作り直せるか |
| 開発機 | ほぼ全部 | CI の runner が本人と同じ OS user で動いていないか・手元の鍵と本番の鍵が別か |
| 暗号の親鍵 | 保存した外部 token・鍵の復号 | 親鍵の差し替え手順があるか |
| アプリ間の合言葉 | その合言葉で名乗れる全利用者・全テナント | 名乗った利用者と対象の行の持ち主を照合しているか |
| 送信の鍵（メール等） | 自社ドメインから任意の宛先へ | 資格の門・回数・差出人の固定・共有枠の使い切り |

## やらないこと

- 値を見て確かめる（「同じ値か」を確かめたくなったら、比べずに作り直す方を選ぶ）
- 人の資格情報で本番を叩いて陰性を確かめる（試験は使い捨ての環境・自動試験・ログで）
- 台帳（攻撃の地図）を repo・チャット・共有 doc に置く
- 「押したので完了」と書く（前後の数えが揃うまで完了にしない）
