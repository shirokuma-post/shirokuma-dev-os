# 鍵の型の移行・作り直しの段取り（7 段）

> 実地で最後まで通した手順（2026-10・Supabase の legacy JWT 型の鍵 → 新しい型の鍵 + 署名鍵の非対称化・複数アプリの本番）。
> 原則: **一度に切り替えない。各段の前後で数え、2 系統で確かめてから次へ。** 人が押す段と AI が数える段を分ける。

| 段 | やること | 誰 | 次へ進む条件（数えるもの） |
|---|---|---|---|
| 1 | コードを新旧どちらの鍵でも動く形にする（例: 鍵をヘッダの置き場所に合わせる・自前の検証を外す） | AI | 全アプリの試験緑・本番に出た |
| 2 | 試験用の新しい鍵で、本番と同じライブラリ・同じ options で読み取りだけ試す | 人が script を打つ / AI がログで照合 | ログで新しい鍵の利用と成功を確認・陰性対照（弱い鍵で強い口が断られる） |
| 3 | 本番用の新しい鍵を作る（用途ごとに別の鍵: サーバー用 / 手元の運用用） | 人（画面） | 鍵の名前で用途が分かる |
| 4 | 新しい鍵を env と手元の file に置く（値を表示しない script で） | 人が script を打つ | 置いた後の行の名前・型・対象・更新時刻だけを確認 |
| 5 | 全アプリを作り直して本番へ（env は新しい build にしか効かない） | AI / 配信担当 | ログで旧い鍵のアプリからの利用が 0・新しい鍵で正常 |
| 6 | 24 時間待って数え直す（夜間のジョブ・定期処理を 1 周含める） | AI | 旧い鍵の利用がアプリから 0（管理基盤自身の通信だけ） |
| 7 | 旧い鍵を無効化 | 人（画面） | 直後・5 分後・10 分後に全アプリ healthy・認証エラー 0（2 系統で） |

## 各段の落とし穴

- **段 2 の陰性対照を省かない**: 新しい鍵で「通った」だけでは、鍵が効いていない可能性を消せない。弱い鍵で強い口が断られることを同時に見る。
- **段 4 の置き換え API**: 保護された env（読み戻せない型）は、置き換えの body に名前を含めると拒否されることがある。値だけを送る（→ `vercel.md`）。
- **段 4 の preview**: 本番 DB の強い鍵を preview の env に残さない。どの branch の build からも読めるため。試験が終わったら preview の行と試験用の鍵を消す。
- **段 5 の見え方**: 同じ sha で作り直すと health の version では新旧を見分けられない。直後の数件は旧い deployment が答えることがある。数分待ってから数える。
- **段 6 で数える窓**: 窓の終わりより前に数えない（時計を確かめてから書く）。終わっていない窓は「途切れ」に見える。
- **段 6 で管理基盤の通信を見分ける**: 管理画面やコマンドツール自身の通信が旧い鍵や既定の鍵で出ることがある。UA で見分け、アプリの利用と分けて数える。既定の鍵は管理画面とコマンドツールが使うので消さない。
- **段 7 の戻し方**: 多くの基盤は無効化した鍵を画面から戻せる。戻し方と制限時間を、押す前に手順書に書く。
- **関連する自前の合言葉**: 旧い共有の秘密（画面から取り出せた値）と同じ値を自前の token の署名に流用していないか、誰も確かめられないなら、**比べずに作り直す**。作り直しの前に、呼び手が「401 を受けたら 1 回だけ token を取り直す」形になっているかを確かめる（なっていないと、取り置きが切れるまで数分失敗が続く）。
